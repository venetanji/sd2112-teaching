## A provenance signal needs a careful interface

**Product update: 3 November 2026.** Anthropic's dated release notes add text watermarking for Claude Mythos 5, Opus 4.7 and Sonnet 4.6 on supported platforms. Its help page says the Amazon Bedrock rollout for these models is due to finish by 10 November; Sonnet 4.6 output may lack the mark with non-default sampling settings. Watermark detection is in private preview for eligible organizations, not an assumed classroom tool.

A detected mark is a limited signal of possible Claude processing. It does not identify the original author or reconstruct the complete history. An absent mark does not establish human-only origin. These are the provider's documented capabilities and limits, not an independently tested detector evaluation.

Sources, checked 4 November: [Claude Platform release notes, 3 November entry](https://platform.claude.com/docs/en/release-notes/overview) · [How Claude marks AI-generated content, availability and limitations](https://support.claude.com/en/articles/16266773-how-claude-marks-ai-generated-content).

**Design question:** What could someone wrongly infer from a “processed with AI” label in your product, and what should the interface help them check?

**Safe paper example:** Invent three cards: a person's text proofread by AI; an AI draft with a verified source; an AI draft with a false claim. Label all three as fictional, not detector results. Discuss separately who contributed, what evidence supports the claim and what the reader should do next. Sketch an explanation and a correction path. Connect the decision to the team's current stage: discover a reader's need, define the claim the product can justify, develop clearer wording, or plan an evaluation. Do not test or upload student work, infer misconduct, or treat a watermark as evidence of truth. No account or detection access is required.

## The agent building a feature and the AI inside it

**Plugin launch: 2 November 2026.** Runway announced packaged Runway Dev plugins for Claude Code, Codex and Cursor, combining account-connected MCP tools with skills for building media features through its API. This is a coding integration, not a new generation model. The accompanying guide, originally published 17 September and updated 2 November, says live generation from an application needs a Runway Dev API key; generation can spend credits. The vendor's end-to-end and quality claims are not measured classroom outcomes.

Sources, checked 4 November: [Runway's dated plugin announcement](https://runway.com/news/developers%2Frunway-dev-plugins-for-coding-agents) · [Runway's integration guide](https://dev.runwayml.com/learn/build-with-your-coding-agent). This differs from the 28 October bridge's App Studio launch: the focus here is an agent implementing a feature in a product.

**Design question:** Which decisions belong to the development agent, the deployed model, written product rules and the person using the product?

**Safe paper example:** For a fictional storyboard helper, draw request → proposed output → human choice → correction. Mark a spending ceiling and a stop point without calling any service. Compare a coding agent helping build that interaction with a model later generating its content. Choose one assumption that needs real evidence and a next action at the team's current Double Diamond stage. This is an invented design exercise, not a built or evaluated product.

No installation, account connection, API-key creation, paid generation, asset upload or public sharing is needed. Use invented text and drawn placeholders. Keep the Week 8 mediation and Week 9 data/bias questions in view; a vendor feature alone establishes neither usefulness nor safety. This file is a reviewable source supplement, not a claim that slides, exports or classroom demonstrations were updated or tested.
